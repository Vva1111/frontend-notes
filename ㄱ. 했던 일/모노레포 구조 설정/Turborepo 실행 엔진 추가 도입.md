### npm Workspaces 를 사용한 모노레포 구성 완료 후 Turborepo 추가 환경 구성


##### Turborepo는 모노레포를 만드는 도구가 아니라, 이미 구성된 모노레포 구조를 빠르고 일관성 있게 운영할 수 있도록 만들어주는 실행 엔진
##### 빌드·테스트·린트·타입 검사에서 실행 순서와 중복 작업을 관리하고 싶을 때 도입을 검토한다.


### 1. 모노레포 운영 엔진 도입 필요성
- 예시 전제: npm Workspaces로 여러 앱과 공통 패키지를 연결한 상태
- 이 상태에서 작업 실행 순서와 캐시를 관리할 필요가 있다면 Turborepo 도입을 검토할 수 있다
- 이유는
	1. **캐싱 ( 로컬 / CI )**
		- 변경 없는 패키지는 build skip
		- CI 빌드 시간 감소
	
	2. **의존성 기반 실행 순서 자동화**
		- 앱이 내부 패키지에 의존하면 dependsOn: ["^build"] 같은 설정으로 공통 패키지를 먼저 빌드한 뒤 앱을 빌드하게 만들 수 있다.
		- 공식 문서에서도 package.json 의존관계를 사용해 패키지 관계를 이해하고, task 를 순서에 맞게 실행한다고 설명한다.
	
	3. **병렬 실행 최적화**
		- Turborepo는 task graph를 바탕으로 "동시에 돌려도 되는 작업"을 병렬화하고 "선행 조건이 필요한 작업"은 순서를 지켜 실행한다.
		- task graph와 scheduler를 통해 incremental concurrent task running을 수행한다. 즉, 단순히 여러 명령을 한번에 날리는 수준이 아니라, 그래프 기반으로 병렬성과 안정성을 함께 가져간다.
	
	4. **변경 영향 범위만 실행 가능**
		- 전체 빌드 대신 변경된 패키지와 그 영향권만 빌드를 실행하는 방식으로 CI, 로컬 빌드 시간이 줄어든다.
	
	5. **CI 최적화**
		- 로컬 캐시 뿐 아니라 remote 캐시를 지원해서 하나의 머신이나 하나의 CI job 에서 만든 결과를 다른 환경이 재사용 할 수 있다.
		- 중복 계산 자체를 줄이는 방식
	
	6. **개발자 경험 표준화**
		- 루트 turbo.json의 task 아래에서 build, test, lint, dev 같은 task를 공통 모델로 정의하면, 각 패키지는 같은 이름의 script만 가지면 된다.
		- task의 각 key가 워크스페이스 내 package.json 스크립트 이름과 매칭 된다. 이는 팀 차원에서 해당 저장소의 build 방식을 한 곳에서 설명할 수 있다는 뜻이다.
	
	- **etc: dev/watch 운영 개선, 디버깅 가능성. 배포 최적화 여지 등**


### 2. 모노레포 운영 엔진으로 Turborepo 도입 이유
1. Turborepo는 기존 패키지의 package.json 스크립트를 가져와서 실행 순서, 병렬 처리, 캐시를 관리하는 방식이다.

2. 이미 구성된 npm Workspaces 구조를 거의 변경하지 않는다

3. 기본 구성은 turbo.json과 기존 스크립트 중심으로 시작할 수 있어 초기 학습 범위를 제한하기 쉽다

4. Vite, Vue, TypeScript 등의 JS/TS 프로젝트와 결합이 잘된다.

5. 로컬/원격 캐시를 지원한다

6. CI 파이프라인에도 별도 종속 없이 붙이기 쉽다.

7. 기존 npm script를 활용할 수 있다.

### Nx 도입 범위를 판단할 때 고려할 조건
1. 참여자의 학습 비용과 도입할 기능의 범위를 함께 고려한다

2. 플러그인과 실행기를 활용하는 범위에 따라 Nx에 대한 의존도가 달라질 수 있다

3. 단순한 스크립트 실행과 캐시만 필요하다면 설정 비용을 비교한다

4. 규모가 작은 경우, Nx의 기능으로 얻는 이득보다 설정/관리 비용이 더 크게 들어갈 수 있다.

5. 단순 빌드와 캐싱만 필요한 경우에는 도구의 기능 범위와 운영 비용을 비교한다

6. 앱과 패키지가 많거나 여러 팀이 함께 작업하는 경우에는 프로젝트 분석 기능의 활용도를 검토한다

7. 앱별 소유권, 모듈 경계, CI 작업 분산이 필요하다면 해당 요구를 지원하는 구성을 검토한다
